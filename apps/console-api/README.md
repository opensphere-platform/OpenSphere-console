# Console API

`C_API` is the Console policy enforcement point. This first target slice accepts durable operations through a constrained PostgreSQL function after checking the current opaque session, permission revision, revoke epoch, risk, reason, AAL, and action policy.

The application role has no direct table write permission. `console_operation.accept_operation` atomically writes the intent, audit-chain event, and outbox event. `console_operation.approve_operation` records one independent AAL2 approver and atomically advances an approval-required operation from `Planned` to `Authorized` using the caller's expected state version. Registry credential material is used only to calculate the canonical payload digest and is never passed to the store. Extension install intake stores only the C_REG-resolved descriptor ID, catalog revision, and exact image as its non-secret execution plan.

The component owns two explicit source areas during the cutover. `src/` is the target C_API authority and implements the foundational operation, identity, Gitea, and Registry contracts. `runtime/` contains the previously verified compatibility runtime so no Console API implementation remains hidden under `backend/`. Moving that source establishes ownership; it does not route browser traffic or grant the target deployment legacy Kubernetes authority. The compatibility runtime is retired only after every authenticated browser family is served through the target owner contracts.

## Runtime

The process requires `CONSOLE_DATABASE_URL` for a login role that inherits only the `console_api` role. `CONSOLE_SUPABASE_SERVICE_ROLE_KEY` is confined to the existing Supabase Auth admin endpoint for initial-administrator create/cleanup, current-subject password recovery-link generation, and exact read-only `/admin/users/{id}` requests for the DB-authorized managed-identity directory. Recovery runs only after opaque-session, CSRF, accepted-intent, and `/user` subject/email checks; managed reads are bounded to 200 subjects with concurrency 8 after the current DB authority check. It is never returned, logged, stored in PostgreSQL, or used for PostgREST/Storage access. `CONSOLE_REGISTRY_URL` selects the fixed internal C_REG origin and defaults to `http://opensphere-registry.opensphere-console.svc.cluster.local:8080`. Supabase status probes use the existing internal services through `CONSOLE_SUPABASE_AUTH_URL`, `CONSOLE_SUPABASE_REST_URL`, and `CONSOLE_SUPABASE_STORAGE_URL`; defaults target the `opensphere-console-data` namespace. `CONSOLE_SUPABASE_PROBE_TIMEOUT_MS` and `CONSOLE_SUPABASE_PROBE_MAX_RESPONSE_BYTES` bound those three parallel reads. Other bounded settings are `CONSOLE_REGISTRY_TIMEOUT_MS`, `CONSOLE_REGISTRY_MAX_RESPONSE_BYTES`, `PORT`, `CONSOLE_DATABASE_POOL_SIZE`, `CONSOLE_DATABASE_CONNECT_TIMEOUT_MS`, and `CONSOLE_DATABASE_IDLE_TIMEOUT_MS`.

```powershell
npm ci --prefix apps/console-api --no-audit --no-fund
$env:CONSOLE_DATABASE_URL = 'postgresql://<limited-runtime-role>@<supabase-postgres>/postgres'
npm start --prefix apps/console-api
```

Implemented routes are self-or-bounded-managed `GET /api/identity`, recent-AAL2 `POST /api/identity/users/{subjectId}/group`, bounded no-secret `GET /api/identity/session/events`, `GET/PUT /api/identity/session/preference`, CSRF/idempotency-bound `POST /api/identity/me/password`, `POST /api/identity/session/login`, `POST /api/identity/session/mfa`, `POST /api/identity/session/touch`, bounded no-secret `GET /api/identity/sessions`, CSRF-bound `DELETE /api/identity/sessions/{sessionId}` and `DELETE /api/identity/sessions`, `GET/DELETE /api/identity/session`, `GET /api/identity/me`, fail-closed `GET /api/identity/supabase/status`, bounded `GET /api/identity/audit`, Registry-backed `GET /api/catalog/entities`, authenticated empty-projection `POST /api/kubernetes/services/{entityName}`, exact installed-lock `GET /api/platform/releases/status`, deterministic recent-AAL2 `POST /api/platform/releases/component-target`, immutable `GET /api/platform/change-templates/{templateId}`, `POST /api/platform/operations`, `GET /api/platform/operations/{operationId}`, `POST /api/platform/operations/{operationId}/approvals`, `POST /api/platform/operations/{operationId}/verification`, Registry credential replace/remove, no-secret Registry connection metadata, exact-digest revocation acceptance/read projection, C_REG-backed `POST /api/admin/extensions/inspect`, C_REG-resolved Extension install intent, `POST /api/admin/extensions/remove`, `GET /livez`, and `GET /healthz`. The password-link route revalidates the current Supabase subject/email, records a no-secret accepted intent, validates the generated internal Auth link, and reconstructs it at the configured public Console origin. A repeated subject/action/key does not call Auth again and returns an unknown-side-effect conflict because one-time link material is not persisted. `/livez` proves only that the process can answer; `/healthz` checks the PostgreSQL authority and is the readiness boundary. Supabase status first revalidates the session and `console.data_identity.read` in PostgreSQL, then performs bounded parallel Auth health, PostgREST OpenAPI, and Storage status reads. A timeout remains `Unknown`, an explicit bad health response is `Blocked`, and migration/backup/restore are not inferred from service health. Catalog reads revalidate the target session, accept only the existing `kind=api` filter and a 1..200 limit, reject stale Registry snapshots, and map the revision-bound C_REG descriptor inventory without Kubernetes credentials. Runtime Resources keeps the current empty `{items: []}` browser contract after session validation; C_API deliberately does not infer live workload state or gain Kubernetes RBAC. Inspect and install accept only `descriptorId` plus exact `catalogRevision`; image and supply-chain evidence come from C_REG. Removal accepts the exact `descriptorId`, reason, and canonical confirmation; Kubernetes identity and observation evidence remain server-derived. C_EXT revalidates approved installs, applies the Kubernetes Registration, and records an exact ready observation. For removal it patches the existing exact Registration to `Uninstalled` and observes the same UID disappear. The verification route accepts only `expectedStateVersion`; its DB RPC derives install, removal, or revocation postconditions from matching C_EXT evidence before moving `Applied` to `Verified`. Registry credential owner dispatch and legacy Backend cutover remain later slices. An operation-intake `202` proves durable intent and an approval `202` proves durable authorization; neither proves installation or removal.

## Kubernetes deployment contract

`deploy.yaml` is the component-owned target manifest. It creates only the C_API ServiceAccount, Deployment, ClusterIP Service, and its ingress/egress boundary. It does not create a database login or a Secret. Before applying it, the installation owner must provision `opensphere-console/opensphere-console-api-runtime` with `database-url`, `session-encryption-key`, and `supabase-service-role-key`; the URL must authenticate a LOGIN role that inherits only the baseline's NOLOGIN `console_api` role. The installer copies the already validated Auth service-role JWT into this C_API-only Secret without printing it. The Supabase owner database password remains prohibited.

`scripts/Install-ConsoleApiRuntime.ps1` is the single target runtime orchestration for C_API, C_EXT, and their fresh Supabase authority. It accepts only official exact digests for C_API, C_EXT, and the four Supabase wrappers plus one HTTPS Console origin. The two namespaces, both namespace pull Secrets, and the exact six-key `opensphere-supabase-secrets` server input must already exist. The script renders `backend/supabase/target/deploy.yaml`, rejects a partial or legacy data stack, brings up PostgreSQL/Auth/Storage-owned schema, applies the one current manifest-bound fresh baseline, waits for PostgREST/Storage, provisions or revalidates separate least-privilege LOGIN/Secret pairs for C_API and C_EXT, then renders and rolls out both component-owned deployments. It refuses split state and implicit credential rotation, keeps credentials on stdin, and rolls back a just-created role/Secret pair if its first verification fails. It does not create namespaces or Supabase server credentials, use the legacy 73-migration installer, or copy the Supabase owner password or JWT-signing secret into either runtime. The already validated service-role JWT is confined to C_API as the single bounded exception for initial-administrator Auth create/cleanup, current-subject password recovery-link generation, and DB-authorized exact managed-user reads. C_EXT receives only its database URL. Session preference and all other non-admin Auth reads use the current subject credential instead.

The image placeholder `__OPENSPHERE_CONSOLE_API_IMAGE__` must be rendered to an exact `ghcr.io/opensphere-platform/opensphere-console-api@sha256:<digest>` reference from the candidate BOM. Network egress is limited to cluster DNS, Supabase PostgreSQL/Auth/PostgREST/Storage, and C_REG. Ingress is limited to the Console Web pod label. No Kubernetes API token is mounted.

The routes listed above are implemented and verified directly against C_API, but the Web proxy does not cut authenticated browser traffic over yet. All 13 target browser-session prerequisites now share the target authority. Session preference, owned session security history, self-service password recovery-link request, managed identity directory, and closed role add/remove are additional actual Web identity routes reconstructed on it. The remaining authenticated owner families still have incomplete target contracts and implementations, so partial routing remains forbidden. This manifest does not make the component boundary release-ready.

The change-template read exposes only the two reviewed compatibility contracts, `foundation-control-plane-bootstrap` and `ceph-rook-prerequisite`, after current `console.git.change` authorization. The returned object is cloned for each request and callers cannot add a template, replace its target, or mutate the server catalog.

Platform Release status reads the existing `opensphere-installation-lock` ConfigMap through a read-only optional volume at `/var/run/opensphere/release/release.json`; C_API receives no Kubernetes token or RBAC. Missing, oversized, malformed, or noncanonical lock evidence fails closed. Component target generation accepts only a recent AAL2 session with `console.git.change`, one exact source revision, a bounded canonical component image map, and a reason. It derives an edge component lock from the installed base without applying it. The target Platform Release owner, execution receipt, and runtime readiness projection are not implemented yet, so status deliberately reports `platform_release_owner_not_target_ready`, `contract: null`, and `execution.ready: false` and the Web cannot submit an apply from this target slice.

The target also implements the internal `GET /api/internal/r2d2-proxy-authn` admission used by OSAA and Manual routes. It accepts only the Nginx internal marker and an original `/api/osaa` or `/api/manual` method/URI, revalidates the opaque browser session and CSRF for non-safe methods, refreshes an expiring Supabase credential through the existing broker, and returns the credential only in `X-OS-R2D2-Authorization` to the internal `auth_request`. The Gateway's target mode then verifies that bearer through C_API `/api/identity/me`; C_API validates Supabase `/user`, binds the Auth `session_id` to a still-active target browser session, and reloads current DB permissions. Target mode and the Nginx upstream must change in the same release render. The compatibility mode remains selected until every authenticated browser family is ready.
