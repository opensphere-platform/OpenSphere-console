# Console data migrations

`baseline/0001_console_authority.sql` establishes the first reconstructed fresh-install authority slice: opaque sessions, subject permission/revoke revisions, permission grants, durable operations, independent approvals, fenced transactional outbox, no-secret Registry connection metadata, Extension revocation execution receipts, explicit verification receipts, and append-only hash-chained audit records. The constrained `console_api` and `console_extension_controller` roles have function execution only. Intake and approval produce `OperationReadyForDispatch`; owner claim/renew use bounded leases and monotonic epochs, while `console_extension.apply_revocation` rechecks the exact claim/action/target/digest before atomically writing the revocation and `Applied` receipt. `console_operation.verify_extension_revocation` independently revalidates the caller and compares the current C_EXT revocation row with the bound `Applied` receipt before moving the operation to `Verified`; callers cannot submit observation evidence. The fixed Registry projection returns configuration and typed verification metadata without credential or SecretRef material. Verification exercises RLS, role isolation, self-approval denial, revocation, stale revision, AAL2, idempotency, concurrent/expired claims, stale fencing, target substitution, observation mismatch, atomicity, and audit continuity against a disposable PostgreSQL instance.

`versions/` is reserved for append-only successors with globally unique IDs, predecessor, semantic key, file digest, and migration-set digest. The legacy `backend/supabase/migrations/0001..0073` history remains evidence; new migrations must not extend that sequence. The baseline is still incomplete until the remaining domain tables, complete role/RLS matrix, upgrade fixture, and isolated restore assertions are added.
