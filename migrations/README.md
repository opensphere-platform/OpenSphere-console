# Console data migrations

`baseline/0001_console_authority.sql` establishes the first reconstructed fresh-install authority slice: opaque session projection/self-revoke, fail-closed Supabase status projection, subject permission/revoke revisions, permission grants, durable operations, independent approvals, fenced transactional outbox, no-secret Registry connection metadata, minimal non-secret Extension execution plans, install/removal Registration and revocation execution receipts, explicit verification receipts, and append-only hash-chained audit records with bounded cursor reads. `versions/0002_browser_session_credential_envelope.sql` adds the encrypted server credential envelope used by password login. `versions/0003_browser_session_mfa_activation.sql` adds two C_API-only functions that read a CSRF-bound pending session and atomically promote the unchanged row to AAL2 after Supabase TOTP verification. `versions/0004_browser_session_refresh_rotation.sql` adds access-credential expiry and three C_API-only functions that read a due refresh envelope, compare-and-set a rotated pair, or revoke the still-current rejected credential family. `versions/0005_browser_session_activity_expiry.sql` keeps the existing session row and C_API boundary, adds the closed persistence policy plus immutable absolute expiry, treats `expires_at` as a 12-hour idle bound, and adds one CSRF-bound activity function whose write rate is capped at once per minute and whose extension cannot exceed absolute expiry. `versions/0006_browser_session_inventory_revocation.sql` adds a bounded no-secret inventory plus CSRF-bound same-subject targeted and all-session revocation through the same row and C_API boundary. `versions/0007` and `0008` keep TOTP enrollment and step-up on the same session row, while `0009` enforces recent AAL2 for privileged operations. `versions/0010_password_recovery_session_revocation.sql` advances the recovered subject's revoke epoch and closes existing sessions. `versions/0011_initial_administrator_bootstrap.sql` adds public-safe required/complete status plus a C_API-only advisory-lock claim that creates exactly one first authority, its eight current permissions, and no-secret audit evidence in one transaction. `versions/0012_browser_session_preference.sql` reads and updates the same subject's next-login persistence through the encrypted session credential, with CSRF and durable no-secret intent before the Supabase Auth write. `versions/0013_owned_browser_session_events.sql` projects only the current subject's closed session-security event set from the existing audit ledger, caps reads at 100, and returns five no-secret fields. `versions/0021_platform_change_permission.sql` adds the single `console.git.change` permission to the existing administrator and operator role policy, advances affected authority revisions, and revokes their old sessions so the new permission cannot appear in an already-issued session. It adds no table or runtime component. `versions/0022_gitea_merge_receipt.sql` adds two C_API-only functions over the existing operation row: a distinct-person recent-AAL2 approval projection and an idempotent merge-revision receipt that moves only `Authorized` to `Submitted`. `versions/0023_gitea_proposal_receipt.sql` records the proposal branch, pull-request number and desired revision once in the existing immutable audit ledger; identical retries perform no write and conflicting coordinates fail closed. These successors add no table, service, queue, framework, or dependency. The constrained `console_api` and `console_extension_controller` roles have function execution only. Self-revoke rechecks current session revisions and atomically records no-token audit evidence. Intake and approval produce `OperationReadyForDispatch`; owner claim/renew use bounded leases and monotonic epochs. Before an install Kubernetes write, C_EXT checks the current fenced claim against the existing exact-image revocation authority. The install receipt transaction and the ready-observation transaction repeat that check, and independent verification refuses a digest revoked after either owner step. A pre-write rejection closes with side effect `none`; a race discovered after Registration application closes with side effect `present`. `console_extension.apply_install_registration` binds the stored C_REG plan to observed Package/Registration versions before recording `RegistrationPresent` and queues a bounded observation. `console_extension.apply_remove_registration` binds the exact descriptor, Package, Registration UID/resourceVersion and fenced claim before recording `RemovalRequested` and queuing the removal observation. C_EXT records `InstallReady` only when Package, Registration generation, workload, supply-chain verification, serving and revalidation evidence agree, and records `RegistrationAbsent` only for the same removed UID. Pending observations reuse the same outbox attempt counter. `record_execution_failure` can close either apply or observation dispatch under its current fence: an exhausted observation becomes `Unknown` with side effect `unknown`, while an explicitly terminal owner result becomes `Failed` with side effect `present`; neither advances verification. `console_extension.apply_revocation` atomically records exact-digest revocation. `console_operation.verify_extension_operation` independently revalidates the caller and compares matching C_EXT evidence before moving an install, removal, or revocation operation to `Verified`; callers cannot submit observation evidence. The fixed Registry projection returns configuration and typed verification metadata without credential or SecretRef material. Audit projection requires current `console.audit.read`, caps each newest-first page at 200 and returns chain hashes without adding mutation grants. Verification exercises RLS, role isolation, single-winner administrator bootstrap, self-approval denial, shell-pinned removal denial, exact-digest revocation at pre-write/receipt/observation/verification gates, stale revision, AAL2, idempotency, concurrent/expired claims, stale fencing, target or UID substitution, install plan binding, bounded observation failure, observation mismatch, MFA replay/CAS, password-recovery session revocation, bounded activity, credential-free audit, atomicity, pagination, and audit continuity against a disposable PostgreSQL instance.

`manifest.json` is the fresh-start migration authority. Every entry has an `opensphere-console/YYYYMMDD/NNNN` global ID, unique semantic key, exact predecessor, canonical-LF file SHA-256, the Git revision that introduced those exact bytes, and the digest and size of its ordered prefix. `node scripts/console-migrations.mjs verify` checks the closed manifest, SQL inventory, file bytes, source revision and complete predecessor/set chain before database access. `apply` uses the existing `psql` client to apply each missing file and its ledger receipt in one transaction; it rejects a live ledger that is not an exact prefix and an idempotent second run performs no writes. `CONSOLE_MIGRATION_DATABASE_URL` is read from the environment and is not printed or passed in process arguments.

`console_migration.applied_migration` is the single required new ledger table. It has no browser, API or controller grants and rejects update, delete and truncate. `GET /api/identity/supabase/status` reports migration `Ready` only when baseline objects exist and the append-only ledger has a complete predecessor chain whose latest set size equals the row count. Direct `psql -f` application is not an authorized path because it omits the atomic ledger receipt.

`versions/` is reserved for append-only successors. The legacy `backend/supabase/migrations/0001..0073` history remains evidence; new migrations must not extend that sequence. The baseline is still incomplete until the remaining domain tables, complete role/RLS matrix, previous-revision upgrade fixture, and isolated restore assertions are added.
